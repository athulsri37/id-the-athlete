# ID the Athlete

A daily deduction game where you identify a mystery athlete using
stat-based clues — Wordle's daily format and shareable results, with a
Guess Who?-style comparison mechanic.

The platform now spans two sports across four tours: **Men's Tennis**,
**Women's Tennis**, **Men's International Cricket**, and **Women's
International Cricket** ("ID the Tennis Player" / "ID the Cricketer").
More sports and tours can be added as data, not code — see
[Architecture](#architecture) below.

## Status

Tennis was the first sport shipped; Cricket followed as a second full
sport built on the same generic schema, with no changes to the core game
engine required. Since then the platform has grown a full Daily
Challenge system (scheduled generation, replay via Past Challenges,
streak tracking), a two-tier closeness-feedback system covering both
sports' different stat shapes, per-sport-calibrated difficulty formulas,
and an internal admin tool for correcting player data and game settings
live, without a redeploy. `dotnet build` (backend) and `npm run build`
(frontend) have been verified to pass cleanly.

## Features

- **Daily Challenge** — one shared mystery player per sport per day,
  generated by a background service on a fixed 00:00 UTC schedule (with
  a startup catch-up run for any day the service missed, and a lazy
  on-demand fallback as a last resort safety net)
- **Past Challenges** — replay any previously-generated daily puzzle you
  missed; explicitly excluded from streak tracking, so catching up never
  inflates or resets your real streak
- **Daily streak tracking** — tracked per-sport in the browser, with a
  replay-lock preventing multiple attempts at the same day's puzzle
- **Practice modes** — Easy / Medium / Hard, unlimited plays, difficulty
  computed live from each player's career stats rather than manually
  tagged (see [Difficulty Tiers](#difficulty-tiers) below)
- **Comparison clues, tailored per sport** — Tennis: 8 clues (Plays,
  Backhand, Country, Grand Slams, Career-High Rank, Turned Pro Year,
  Career Titles, Active/Retired status). Cricket: 9 clues (Country,
  Batting Hand, Bowling Style, Role, Combined Matches, Combined Runs,
  Combined Wickets, Debut Year, Active/Retired status)
- **Closeness-tier feedback** — clues show a distinct "close" state (not
  just match/miss) when a guess is near the correct answer:
  - **Numeric** — fixed thresholds for Tennis (e.g. career-high rank
    within 5); dynamic percent-of-value-plus-floor thresholds for
    Cricket, tuned per stat via `AppSettings` (e.g. wickets within 15%
    of the answer, or 15 wickets, whichever is larger — so low counts
    still get a sane floor)
  - **Categorical** — Cricket's Role and Bowling Style clues use
    tag-based matching (e.g. "Batting All-rounder" reads close to
    "Bowling All-rounder" since both share the All-Rounder tag; a pace
    bowling style reads close to another pace style, not to spin)
  - **Country** — true land-border adjacency for Tennis (e.g. France ↔
    Spain), regional-bloc grouping for Cricket (e.g. Pakistan ↔
    Bangladesh, both grouped under the same Asia bloc) rather than
    simple distance
  - All closeness behavior is individually toggleable via `AppSettings`
- **Country hint** — after 5 guesses without identifying the correct
  country, players can optionally reveal it for free (doesn't count
  against the guess limit)
- **AI-generated post-game trivia** — a short blurb about the mystery
  player shown on game over; optional, requires an Anthropic API key
  (see [Getting Started](#getting-started)) and a separate enable/disable
  toggle in `AppSettings`
- **Retro and Stadium themes** — two full visual themes switchable via a
  single `AppSettings` row (see [Theme System](#theme-system))
- **Shareable results** — Wordle-style emoji grid via the Web Share API /
  clipboard, no social media API integration required
- **Internal admin tool** — a key-protected interface, not linked from
  the public UI, for editing player stats and difficulty overrides and
  toggling game settings live against the running database (see
  [Admin Tool](#admin-tool) below)
- **Generic, sport-agnostic schema** — the data model (Sport → Player →
  AttributeDefinition → PlayerAttributeValue) is what let Cricket ship
  as a second sport without any changes to the schema or the core
  comparison engine; see [Architecture](#architecture)

## Difficulty Tiers

Difficulty is computed live from each player's career stats, not
manually tagged, and the formula is calibrated per sport (and, for
Cricket, per gender) rather than shared wholesale:

- **Tennis** (shared formula, Men's and Women's): Easy if the player
  reached world #1, has 20+ career titles, or has 2+ Grand Slam titles;
  Medium for 5-19 titles; Hard otherwise.
- **Cricket, Men's**: Easy if combined runs ≥ 10,000, wickets ≥ 300, or
  matches ≥ 300; Medium at runs ≥ 3,000, wickets ≥ 100, or matches ≥ 150;
  Hard otherwise.
- **Cricket, Women's**: separately calibrated with lower thresholds
  (Easy at runs ≥ 8,000 / wickets ≥ 250 / matches ≥ 250; Medium at
  runs ≥ 2,500 / wickets ≥ 90 / matches ≥ 130) — the Men's thresholds
  badly under-served the Women's roster when shared as-is, placing only
  ~9% of players in Easy against a median career of 139 matches / 1,912
  runs / 75 wickets.

A per-player manual override (`IsOverridden` / `DifficultyOverride`) lets
a curator pin a specific player to a tier when raw stats don't reflect
real-world recognizability, editable live via the admin tool.

## Architecture

The core design decision that made adding Cricket a data-only change is
a fully generic, sport-agnostic schema:

```
Sport → Player → AttributeDefinition → PlayerAttributeValue
```

Every stat, for every sport, is a `(Player, AttributeDefinition) → Value`
row rather than a dedicated column — Tennis's "Career Titles" and
Cricket's "Combined Wickets" are stored the same way, keyed by an
`AttributeDefinition.Key` string the frontend and comparison engine read
generically. Adding a sport means inserting rows (a `Sport`, its
`AttributeDefinition`s, its players and their `PlayerAttributeValue`s)
and, where a sport's stats genuinely behave differently, adding a
sport-specific branch in the small set of services that need to know the
difference (difficulty tiers, closeness thresholds) — never a schema
change, and never a change to `GameController`, `PlayersController`, or
the frontend's game-flow components, all of which are entirely
sport-agnostic (routed by `{sportSlug}`).

```
id-the-athlete/
├── backend/IdTheAthlete.Api/
│   ├── Models/          # Sport, Player, AttributeDefinition, PlayerAttributeValue, DailyPuzzle, AppSetting
│   ├── Data/             # GameDbContext
│   ├── Migrations/       # EF Core migrations (generated, committed)
│   ├── Geo/               # CountryProximity (Tennis land-border adjacency)
│   ├── Rules/             # Per-sport-family scoring: ISportRules, TennisRules, CricketRules, SportRulesRegistry
│   ├── Middleware/        # AdminAuthMiddleware (protects /api/admin/*)
│   ├── Errors/            # NotFoundException / InvalidRequestException + the central handler that turns them into problem responses
│   ├── Services/
│   │   ├── GameService.cs                  # Orchestration: guess submission, session/daily-puzzle resolution
│   │   ├── DifficultyService.cs            # Curator override, else the sport family's difficulty formula
│   │   ├── PracticeSessionService.cs       # In-memory practice-mode sessions, dropped after PracticeSessions:IdleTimeout (default 90 min) without a guess
│   │   ├── DailyPuzzleService.cs           # Daily puzzle selection, lookup, persistence
│   │   ├── DailyPuzzleGenerationService.cs # Background service: 00:00 UTC scheduled generation + startup catch-up
│   │   ├── AiTriviaService.cs              # AI trivia blurb generation
│   │   ├── GameTriviaService.cs            # Unlocks a finished game's trivia from its trivia token
│   │   └── AdminService.cs                 # Backs the internal admin tool
│   ├── Controllers/      # PlayersController, GameController, SettingsController, AdminController
│   └── Dtos/             # Request/response contracts
├── scripts/               # db-backup.sh / db-restore.sh (the database is the source of truth)
├── tools/                 # Roster research agent (Python): researches, checks and adds players
└── frontend/src/
    ├── api/              # Axios client
    ├── components/       # PlayerSearch, ClueGrid, ClueLegend, ShareResult
    ├── hooks/             # useGameTrivia (fetches a finished game's trivia blurb)
    ├── pages/             # HomeScreen, TourSelect, SportHome, GameBoard, PastChallenges (home → tour → sport → game flow)
    ├── admin/             # Login gate, tab shell, player editor, settings editor — the internal admin tool
    ├── utils/              # dailyStreak, dailyCompletion, localDate (UTC-aligned "today" helpers)
    ├── styles/             # index.css (Tailwind entry), themes.css (retro/stadium theme variables)
    └── types/
```

## Getting Started

### Prerequisites

- [.NET 10 SDK](https://dotnet.microsoft.com/download)
- Node.js 24 (the version in `frontend/.nvmrc`; CI uses the same)
- PostgreSQL (via Docker or a local install)

### 1. Start PostgreSQL

Easiest via Docker:
```bash
docker compose up -d postgres
```
Or point `ConnectionStrings:DefaultConnection` in `appsettings.json` at your
own local Postgres instance.

### 2. Set up the database (EF Core migrations)

Migrations are already committed to the repo (`Migrations/`), so a fresh
clone just needs to apply them:
```bash
cd backend/IdTheAthlete.Api
dotnet tool install --global dotnet-ef   # if you don't have it already
dotnet ef database update
```
The app also calls `db.Database.Migrate()` on startup, so the schema stays
in sync automatically after that. On an empty database the migrations also
create the reference data: the four sports, their clue columns and the
default settings. They don't create any players.

To get the players, restore a backup of an existing database (see
[Player Data & Backups](#player-data--backups) below):
```bash
scripts/db-restore.sh backups/<file>.dump
```

Only run `dotnet ef migrations add <Name>` if you're introducing new
schema changes going forward — it's not needed for initial setup.

### 3. (Optional) Enable AI trivia blurbs

On game over, the app can show a short AI-generated trivia blurb about the
mystery player. This is optional — without a key configured, the game works
exactly the same, just without the blurb. Set your Anthropic API key via
`dotnet user-secrets` rather than committing it to `appsettings.json`:
```bash
cd backend/IdTheAthlete.Api
dotnet user-secrets init
dotnet user-secrets set "Anthropic:ApiKey" "sk-ant-..."
```
Trivia generation is also gated by the `AiTriviaEnabled` setting in the
`AppSettings` table, which defaults to `false` (off). So configuring an API
key alone isn't enough to turn the feature on, and removing the key isn't
the only way to turn it off. Switch it on or off from the admin tool's
Settings tab (see [Admin Tool](#admin-tool)).

### 4. (Required for the admin tool) Set an admin key

The internal admin tool (see [Admin Tool](#admin-tool) below) is
protected by an `X-Admin-Key` header, checked against any value under the
`AdminKeys` config section — also set via `dotnet user-secrets`, never
committed:
```bash
cd backend/IdTheAthlete.Api
dotnet user-secrets set "AdminKeys:YourName" "some-long-random-string"
```
The key under `AdminKeys` is just a human-readable label for bookkeeping
(e.g. `AdminKeys:Athul`) — any number of admins can each have their own
entry, and adding one is config-only, no code or deploy change needed.
Without at least one key configured, the admin tool is unusable but every
other part of the app works normally.

### 5. Set a game token signing key

Daily Challenge guesses are counted by the server through a signed token,
so the answer is only revealed after 8 real guesses. The token is signed
with `GameTokens:SigningKey`, which must be a random string of at least 32
characters:
```bash
cd backend/IdTheAthlete.Api
dotnet user-secrets set "GameTokens:SigningKey" "<random string, 32+ characters>"
```
In Development the app still starts without it, using a random key for that
run (in-progress daily games then don't survive a restart). In any other
environment it refuses to start until the key is set, as the
`GameTokens__SigningKey` environment variable. Changing the key only
restarts daily games that are in progress.

### 6. Run the backend
```bash
dotnet run
```
API will be available at `http://localhost:5080`, with interactive OpenAPI
docs (via Scalar) at `http://localhost:5080/scalar/v1`.

### 7. Run the frontend
```bash
cd frontend
npm install
npm run dev
```
App will be available at `http://localhost:5174`.

### Running it all in Docker

`docker compose up --build` runs Postgres, the API and the production
frontend together, with the site at `http://localhost:5174`. Set
`GAME_TOKEN_SIGNING_KEY` (32+ characters) in your shell first: the API
container runs in Production mode and won't start without it. A fresh
database has no players; restore a backup to get them.

The frontend image (`frontend/Dockerfile`) builds the static site with
Node 24 and serves it with nginx, as a non-root user, on `$PORT` (default
8080), so any host that assigns a port works. The API address is baked in
at build time:
```bash
docker build --build-arg VITE_API_BASE_URL=https://<api host> -t idtheathlete-frontend frontend
```
The API must list the site's origin in `AllowedOrigins`. Hashed assets are
cached for a year; the page itself is revalidated on every visit, so a new
deploy shows up straight away.

## Testing

The project has three independent test layers, all run by CI on every pull
request (see [Continuous integration](#continuous-integration)). The backend
suite covers the game rules (clue scoring for every sport, difficulty tiers,
guess counting, practice-game expiry, settings fallbacks); the frontend suite
covers daily streaks and completions, trivia fetching and error messages; the
end-to-end suite is still a single smoke test.

### Backend unit tests

xUnit project (`backend/IdTheAthlete.Api.Tests`), referencing
`IdTheAthlete.Api` directly so tests can exercise services like
`DifficultyService` and each sport family's rules without going through
HTTP. `ClueClosenessTests` pins down how every clue is judged for each
sport, end to end through `GameService`. Uses
`Microsoft.EntityFrameworkCore.InMemory` for a `DbContext` without a real
Postgres database, and `Moq` to mock dependencies.
```bash
cd backend/IdTheAthlete.Api.Tests
dotnet test
```

### Frontend unit tests

Vitest + React Testing Library, covering pure utility functions and,
eventually, components.
```bash
cd frontend
npm test
```

### End-to-end tests (Playwright)

Playwright drives the app through a real browser against the actual
running dev servers — it does not start them itself. **Both the backend
and frontend dev servers must already be running** (see
[Getting Started](#getting-started) steps 5 and 6) before running this
suite:
```bash
cd frontend
npx playwright install chromium   # one-time browser install
npm run test:e2e
```

### Continuous integration

`.github/workflows/ci.yml` runs on every pull request to `main` and every
push to it, in parallel jobs:

- **Backend tests:** `dotnet test`.
- **Frontend tests, type check and build:** `npm test`, `npm run build`.
- **Roster agent checks:** the Python unit tests in `tools/`.
- **Docker images build:** builds the backend and frontend images, then
  checks that the frontend image serves the site on an assigned port, with
  the API address baked in and no Node in the image.
- **Migrations and app smoke test:** against an empty Postgres, checks that
  every model change has a migration, applies the migrations, checks the
  reference data, starts the API in Production mode and the frontend, and
  runs the Playwright suite.

`.github/workflows/pr-description.yml` adds one more check on pull
requests: `scripts/check-attribution.sh --description` fails if the PR
description carries an AI attribution line. PRs are squash-merged with the
title and description as the commit message, so the description is what
reaches `main`. It reruns whenever the description is edited.

`main` is protected: a PR merges only when all of these checks pass on a
branch that's up to date with `main`.

CI uses no secrets and no paid APIs, and never touches a real database. It
can't replace the checks against a copy of the dev data before opening a
PR (CLAUDE.md, Definition of done), since the CI database has no players.

## Player Data & Backups

The database is the single source of truth for player data. Players,
curator edits, difficulty overrides, settings and daily puzzles exist
nowhere else, so back it up.

- **Adding players:** run the roster research agent in `tools/`. It
  researches candidates, checks every value against what the game accepts,
  shows each player's difficulty tier, and writes the ones you accept. See
  the instructions at the top of `tools/roster_research_agent.py`, e.g.
  `python roster_research_agent.py tennis-women 10 --tiers medium,hard`.
- **Correcting a player** or setting a difficulty override: use the
  [Admin Tool](#admin-tool).
- **Backing up:** `scripts/db-backup.sh` writes a timestamped dump to
  `backups/` (git-ignored). Take one before anything risky and keep copies
  somewhere other than this PC.
- **Restoring:** `scripts/db-restore.sh backups/<file>.dump` replaces the
  target database with the backup, after you type its name to confirm.

Both scripts target the local Docker database by default; set `DB_NAME` for
another local database or `DATABASE_URL` for any other server.

### Filling production for the first time

After the first deploy (the app has started once, so migrations have run):
```bash
scripts/db-backup.sh
DATABASE_URL='postgresql://user:pass@host:5432/db' scripts/db-restore.sh backups/<that file>.dump --skip-puzzle-history
```
`--skip-puzzle-history` leaves out your local daily puzzles, so production's
Past Challenges start on launch day. Restart the API afterwards so it
creates today's puzzle.

### Adding a new sport

A new sport is one PR: a migration that inserts its `Sports` and
`AttributeDefinitions` rows (like `AddReferenceData`), an `ISportRules`
class for its scoring, an entry in `frontend/src/config/sportFamilies.ts`,
and a profile in the roster agent's `SPORT_PROFILES`. Then add its players
with the agent.

## API Endpoints

Every gameplay route is sport-agnostic, parameterized by `{sportSlug}`
(one of `tennis-men`, `tennis-women`, `cricket-men-international`,
`cricket-women-international`):

- `GET /api/sports` — every playable tour with its family and short label (builds the home and tour-select screens)
- `GET /api/sports/{sportSlug}/players` — full player pool (for guess autocomplete)
- `GET /api/sports/{sportSlug}/attributes` — this sport's ordered clue columns
- `GET /api/sports/{sportSlug}/daily-puzzles` — every date with an existing Daily Challenge, for Past Challenges
- `POST /api/sports/{sportSlug}/game/start?difficulty=easy|medium|hard` — start a practice game, returns a `sessionId` (expires after 90 minutes without a guess or hint, or on restart)
- `POST /api/sports/{sportSlug}/game/guess` — submit a guess, returns per-attribute clue feedback (daily games pass back the `gameToken` from the previous guess); the game-over guess also returns a `triviaToken`
- `GET /api/sports/{sportSlug}/game/trivia?triviaToken=...` — the finished game's AI trivia blurb, or null when unavailable; fetched after the result is shown so the final guess never waits on the AI call
- `GET /api/sports/{sportSlug}/game/hint/country?mode=...&sessionId=...&gameToken=...` — free hint after 5 guesses (enforced by the server), reveals only the mystery player's country
- `GET /api/settings/theme` — the currently active visual theme

Every error is a standard problem response (RFC 9457,
`application/problem+json`) with a human-readable `detail`: 404 when the
resource named in the route doesn't exist (e.g. an unknown `{sportSlug}`),
400 for a bad value in the body or query string or a broken game rule, 401
for a missing admin key, and 500 with no details for anything unexpected.

## Theme System

The app ships with two visual themes — **retro** and **stadium** —
controlled by a single row in the `AppSettings` table (`Key` =
`"ActiveTheme"`; with no such row the theme is `"retro"`). The frontend reads the
active theme from `GET /api/settings/theme` on load and applies it via a
`data-theme` attribute on the document root, which the CSS variables in
`frontend/src/styles/themes.css` key off of.

To switch themes, set that row directly in the running Postgres container
(this creates the row if it doesn't exist yet):
```bash
docker compose exec postgres psql -U idtheathlete -d idtheathlete \
  -c "INSERT INTO \"AppSettings\" (\"Key\", \"Value\") VALUES ('ActiveTheme', 'stadium') ON CONFLICT (\"Key\") DO UPDATE SET \"Value\" = EXCLUDED.\"Value\";"
```
Swap `'stadium'` for `'retro'` to switch back. Refresh the frontend to see
the change take effect.

## Admin Tool

An internal, key-protected admin interface — not linked from the public
UI — lets a curator browse any sport's roster, edit a player's raw stats
or set a difficulty override, and edit any existing `AppSettings` row
(closeness feature flags and thresholds, AI trivia) directly against the
running database, without a redeploy. It authenticates via the `X-Admin-Key`
header described in [Getting Started](#getting-started) above and has no
other session or account system.

## Notes on the dataset

As of October 2026 the dataset contains **723 real athletes** across two
sports, individually researched — not placeholder or sample data:

| Tour                          | Players |
|--------------------------------|---------|
| Men's Tennis                   | 200     |
| Women's Tennis                 | 134     |
| **Tennis total**                | **334** |
| Men's International Cricket     | 259     |
| Women's International Cricket   | 130     |
| **Cricket total**                | **389** |
| **Grand total**                  | **723** |

Tennis spans current tour players, the 2005–2015 golden era, and
historical legends going back to the pre-Open Era. Cricket spans current
international players and recent-era greats across both the Men's and
Women's international game.

New players are added with the roster research agent (see
[Player Data & Backups](#player-data--backups)).

Player stats (Grand Slam counts, titles, career runs/wickets, etc.) are
accurate as of mid-2026 but will drift for active players over time —
treat this as a dataset that needs periodic manual refreshes, not a live
feed.
